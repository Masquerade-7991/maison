## Commands

```bash
npm run dev          # Next dev server (rewrites the agent-rules block in AGENTS.md)
npm run build        # Production build — also the only full typecheck (tsc has noEmit)
npm run lint         # ESLint (flat config, eslint-config-next core-web-vitals + TS)

npm run db:generate  # Emit SQL migrations from src/db/schema.ts into ./drizzle
npm run db:migrate   # Apply migrations
npm run db:push      # Push schema straight to the DB (no migration file) — dev only
npm run db:studio    # Drizzle Studio
npm run db:seed      # Re-seed the catalogue from scripts/seed.ts (clears it first)
```

`node_modules` is pnpm-managed: install with `pnpm add`, never `npm install` (`package-lock.json` is stale). `npm run <script>` still works. pnpm refuses to run anything unless `allowBuilds` in `pnpm-workspace.yaml` holds real `true`/`false` values.

No test runner is configured yet. `node src/lib/listing.check.mjs` asserts the listing filters/sorts and every `stockState` branch.

## Architecture

Next.js 16 App Router + React 19, Tailwind v4 (PostCSS plugin only — no `tailwind.config`; theme lives in `src/app/globals.css`), TypeScript strict, `@/*` → `src/*`.

**Data layer.** `src/db/index.ts` creates a single `db` over Neon's HTTP driver (`drizzle-orm/neon-http`) and throws at import time if `DATABASE_URL` is missing. That driver is stateless HTTP — no interactive transactions, so batch via `db.batch()` rather than `db.transaction()`. `DATABASE_URL` must be the **pooled** Neon string. `npm run build` needs it too: `generateStaticParams` reads product slugs from the database.

**Neon.** One environment by choice: the repo is linked (`.neon`, gitignored) to project `flat-frost-80736700`, branch **`production`**, and development, migrations and seeding all run against it. Get the URL with `neon connection-string production --pooled`. Link with `--no-env-pull`, because the default env pull writes into `.env`. `db:seed` **wipes and rewrites the live catalogue**: once real products exist, stop using it (or seed a throwaway branch instead).

**Schema.** `src/db/schema.ts` is the single schema file and the source of truth for `drizzle.config.ts`, the `db` client, and the Better Auth adapter. It holds the four Better Auth tables (`user`, `session`, `account`, `verification`, migration `0001`) plus the catalogue (`categories`, `products`, `product_images`); every further application table belongs in the same file. Renaming or dropping the Better Auth columns breaks auth. The auth block is CLI output kept verbatim. To change it (e.g. after adding a Better Auth plugin), run `npx auth@<better-auth version> generate --config src/lib/auth.ts --output <scratch file>` and paste the result in. The old `@better-auth/cli` package stopped at 1.4. Never point `--output` at `schema.ts`: it overwrites the catalogue. Conventions: camelCase TS keys mapped to snake_case columns via `casing: "snake_case"`, which must be set in **both** `drizzle.config.ts` and the `drizzle()` call, or migrations and queries disagree on column names; `uuid` primary keys with `defaultRandom()` on application tables, with `slug` as the unique public identifier every route and React key uses; declare each foreign key's `relations()` alongside the table.

**Catalogue.** Schema decisions the storefront depends on:

- **Money is integer cents** (`priceCents`, `compareAtCents`). Only `mapProduct()` in `src/lib/products.ts` divides by 100; components receive dollars and never see the column.
- **Stock is a quantity plus a flag** (`stockQuantity`, `madeToOrder`), never a stored state. The four states the UI speaks in are derived by `stockState()` in `src/lib/stock.ts`, which also owns `stockCopy` and `stockTone`. `stockDetail` is editorial free text beside them. Stock is per product: with no variants, the size picker is a display-only list by category and sizes are not stocked.
- **Homepage order comes from `products.createdAt` descending**, not from a featured or "new" flag — the grid takes the newest 8 (a "rail" of the next 5 is not built yet). "New" (badge and `/new-arrivals`) is derived as the newest `NEW_COUNT` (12) by a subquery, never stored.
- **Categories carry the homepage "Collections" strip**: the ones with an `imageUrl` are what it renders, and piece counts are counted from `products`, never stored.
- **`product_images.alt` belongs to the row, not the asset** — the same URL is reused across products with different copy. `position` 0 is the packshot.
- Pages never touch `db` directly: they call the query functions in `src/lib/products.ts`, which return the mapped `Product` type. `src/lib/sample-data.ts` is now static chrome only (hero, atelier, services, nav) and holds no catalogue data. Listing filters/sorts are pure functions in `src/lib/listing.ts`, run in memory over one view's products. That is a deliberate ceiling: move them into the SQL `where` once a single view holds a few hundred products.
- **Categories are product types** (ready-to-wear, bags, shoes, accessories, jewellery). Department (`women`/`men`/`unisex`) is an enum column, and `isGift` a flag. Listing routes: `/collections/[slug]` (by category), `/women` and `/men` (department, both include unisex), `/gifts`, `/new-arrivals`; all share `src/components/product-listing.tsx`.- Drizzle relational queries: write the `with` block inline at each call site. Hoisting it into a shared `as const` config breaks result-shape inference. Relational queries alias the outer table, so raw subqueries inside `extras`/`orderBy` need their own alias (`from products p2`). The `extras` callback receives columns, not the table, so type its parameter as `{ col: AnyColumn }`.

**Migrations.** Versioned SQL committed under `drizzle/`, generated with `db:generate` and applied with `db:migrate`; `db:push` stays a dev-only escape hatch. Read the emitted SQL before applying it. `scripts/seed.ts` (run via `db:seed`, under `tsx` with `import "dotenv/config"`) is idempotent — it clears `product_images` → `products` → `categories` in that order, and backdates `createdAt` from a hardcoded base date so ordering is reproducible across runs.

**Auth.** `src/lib/auth.ts` is the server instance: Drizzle adapter, email/password with `requireEmailVerification` (no session until the link is clicked; duplicate sign-ups get the same generic reply as new ones). Sign-in, sign-up and sign-out run from client components through `src/lib/auth-client.ts` and the `/api/auth/[...all]` routes, **not** Server Actions calling `auth.api.*`: Better Auth's rate limiting only runs in its HTTP router, so server-side calls would bypass it. A `hooks.before` on `/sign-up/email` deletes an unverified account whose link has expired, so a stranger's sign-up can't reserve an address for good. Verification mail goes through `src/lib/email.ts` (Resend over `fetch`); without `RESEND_API_KEY`/`EMAIL_FROM` in dev the link is printed to the server log **and shown on the sign-up page** (and in the unverified sign-in notice) via `getDevVerificationLink` in `src/lib/dev-email-actions.ts`, which returns null whenever email is configured or `NODE_ENV` is production: showing the link on a live site would let anyone verify an address they don't own. In production a missing key throws.

**Sessions and roles.** Server code reads the session only through `src/lib/session.ts`: `getSession()` (React `cache`, no cookie cache, so sign-out and role changes apply on the next request), `requireUser(next)` and `requireAdmin()` for pages, `assertAdmin()` for admin Server Actions and data functions (they are public endpoints, so they throw rather than redirect). Call these in every protected page and action, never only in a layout: layouts don't re-render on client navigation. There is no `proxy.ts`. Customers get a 404 from admin pages, so the routes aren't advertised. `user.role` (`customer` | `admin`) is a Better Auth `additionalField` with `input: false`; only `npm run auth:set-role -- <email> <role>` (the way to create the first admin) and the `/admin` page can change it, and an admin can't change their own role. Redirect targets from `?next=` go through `safeNext()` (same-site paths only).

**Bag.** Built; checkout is not. The bag is DB-backed and signed-in only: one `cart_items` table keyed by `(user_id, product_id, size)`, no parent `carts` table, so there is no guest bag and nothing to merge on sign-in. `size` is the display-only size from `detailsFor()` (`""` for one-size categories); stock is per product, so a product's sizes share one allowance. `src/lib/cart.ts` is the only module that touches `db` for carts, the way `src/lib/products.ts` owns the catalogue; rules and shapes (`maxAllowed`, `lineMax`, `subtotalCents`, `BagLine`) live in `src/lib/cart-rules.ts` so client components can import them without pulling in `db` (`node src/lib/cart-rules.check.mjs` covers them). **`cart_items` stores no price**: amounts are read live from `products.priceCents` on every render, and forms send only a slug, a size and a quantity. The Server Actions in `src/lib/cart-actions.ts` are public endpoints: each reads the session, validates every field and re-checks live stock (`maxAllowed`: stock capped at 10, made-to-order always 10, sold out 0; the DB also checks `quantity between 1 and 10`). The bag holds no reservation: stock that drops after adding shows as a notice on `/bag` (`lineIssue`), the bag is never changed on read, and checkout must re-check. Products cascade to `cart_items`, so `db:seed` empties every bag.

**Checkout.** Stripe-hosted Checkout Sessions (test mode: "Maison sandbox"). `startCheckoutAction` in `src/lib/checkout-actions.ts` posts an **empty form**: it re-reads the bag with `getBag()` (the authoritative stock check; any `hasIssues` blocks checkout), snapshots it into a **pending order** (`createPendingOrder` in `src/lib/orders.ts`, our prices), and creates the session from that snapshot with `price_data`. There are no Stripe Products or Prices and no sync job; Stripe never receives an amount the browser supplied. Before creating a session it closes the user's older open sessions (an already-paid one is applied instead, so no payment is lost). Sessions expire after 30 minutes, which is also the accepted oversell window (no stock reservation). Never pass `payment_method_types` (dynamic payment methods), keep `integration_identifier`, and use a restricted `rk_` key with *Checkout Sessions: write*. `src/lib/stripe.ts` validates keys on first use, so the storefront builds and runs without them. Tax is off (Stripe Tax needs a registration) and shipping addresses are collected for the US only (`SHIP_TO`).

**Orders move forward only on Stripe-verified facts.** `applyCheckoutSession` in `src/lib/orders.ts` is the single fulfilment function. Its input is always a Checkout Session that came from Stripe itself, never from the browser: the webhook (`src/app/api/stripe/webhook/route.ts`, signature-verified over the raw body, handling `checkout.session.completed`, `async_payment_succeeded`, `async_payment_failed` and `expired`; 500 when `STRIPE_WEBHOOK_SECRET` is unset, so Stripe retries) is the primary path. `/checkout/success` and the checkout action's older-session sweep are the **fallback** for a webhook that is late or never arrives (e.g. `stripe listen` not running): both `sessions.retrieve()` on the server with our key and apply it through `sessionEvent()`, which maps a fetched session onto the equivalent event (a failed delayed payment is known only from its webhook). The `session_id` in the success URL is only a lookup key; the page 404s unless `client_reference_id` is the signed-in user, and still shows "confirming" (polling with `AutoRefresh`) if the order is pending while Stripe says complete. If the sweep settles an older paid order, checkout stops and asks the customer to review the bag, so the same pieces are never charged twice. Status transitions come from `nextStatus()` in `src/lib/order-rules.ts` (`pending → processing/paid/payment_failed/expired`, forward only, with an unknown `payment_status` never counting as paid; `node src/lib/order-rules.check.mjs`). Each transition is **one SQL statement** (CTEs; neon-http has no transactions) guarded by `status = <current>`. Only the call that actually moves an order to `paid` decrements stock (floored at 0, made-to-order skipped, `stock_shortfall` set if stock ran short) and deletes the paid lines from the bag. That guard is what makes duplicate or concurrent deliveries harmless; there is no event table. The webhook returns 500 on a database error so Stripe retries. `order_items` snapshot name, slug, size and unit price (`product_id` is `set null`), and `orders.user_id` is `restrict`, so re-seeding or catalogue edits never break order history. Keep `/api/**` out of any future `src/proxy.ts` matcher: Stripe sends no cookie. **Order history** is `/account/orders` (`listOrdersForUser`, expired checkouts hidden) and `/account/orders/[id]`; both scope by the session's user id, so another customer's order id is a plain 404. The detail page, like `/checkout/success`, re-checks a pending or processing order against Stripe (`sessions.retrieve` + `sessionEvent`) so a missed webhook never leaves it stale; a Stripe error just shows the stored state. Items, totals and delivery render through `OrderDetails` (`src/components/order-details.tsx`), shared with `/checkout/success`.

**The header bag count has no number on the four catalogue routes.** `/`, `/new-arrivals`, `/collections/[slug]` and `/products/[slug]` pass no `bag` slot to `SiteHeader` on purpose: any server read of `headers()` in that shell makes them dynamic and kills `revalidate = 300` and `generateStaticParams`. Do not "fix" the missing count with a server component; fetch it from a client component after hydration if it is ever wanted there.

**Money formatting.** `currency` in `src/lib/format.ts` rounds to whole dollars and is **catalogue-only**. Anything derived from cents — bag, checkout, receipts — uses `formatCents`, or `$99.99` renders as `$100` next to a Stripe page that says otherwise.

Env: copy `.env.example` → `.env`. Claude cannot read or write `.env` (denied by permissions), so the user pastes secrets such as `DATABASE_URL` themselves. Auth needs `BETTER_AUTH_SECRET` (`openssl rand -base64 32`) and `BETTER_AUTH_URL` (the app's origin, or verification links break); sending real email needs `RESEND_API_KEY` and `EMAIL_FROM`. Checkout additionally needs `STRIPE_SECRET_KEY` (a restricted `rk_` key with Checkout Sessions: write) and `STRIPE_WEBHOOK_SECRET` (from `stripe listen --events checkout.session.completed,checkout.session.async_payment_succeeded,checkout.session.async_payment_failed,checkout.session.expired --forward-to localhost:3000/api/stripe/webhook` locally; current CLIs refuse to start without `--events`. The secret is stable per machine, see `stripe listen --print-secret`; or the endpoint's own signing secret when deployed). `src/lib/stripe.ts` validates these on first use rather than at import, so the storefront still builds and runs without them — only checkout and the webhook fail.

## Next.js 16 notes

Route params and `searchParams` are Promises and must be awaited. Layouts/pages use the globally generated `LayoutProps<"/route">` / `PageProps<"/route">` types (see `src/app/layout.tsx`) — these are emitted into `.next/types`, so a route's types only exist after a dev server or build has run. Read `node_modules/next/dist/docs/` before relying on remembered APIs. After renaming a dynamic segment (e.g. `[id]` → `[slug]`), restart the dev server: it keeps the old route cached and throws "different slug names for the same dynamic path". Stale `.next/types` from an old `next build` break `tsc` the same way. Only one `next dev` may run per `distDir`, and Tailwind scans every folder that isn't gitignored: a second build output under another name (e.g. for a test server) gets its binaries scanned into garbage classes that break `globals.css`, and the broken CSS survives in `.next/dev` until that folder is deleted.
