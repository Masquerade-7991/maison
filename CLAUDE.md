## Commands

```bash
npm run dev          # Next dev server (rewrites the agent-rules block in AGENTS.md)
npm run build        # Production build — also the only full typecheck (tsc has noEmit)
npm run lint         # ESLint (flat config, eslint-config-next core-web-vitals + TS)

npm run db:generate  # Emit SQL migrations from src/db/schema.ts into ./drizzle
npm run db:migrate   # Apply migrations
npm run db:push      # Push schema straight to the DB (no migration file) — dev only
npm run db:studio    # Drizzle Studio
npm run db:seed      # Re-seed the catalogue from scripts/seed.ts (clears it first)
```

`node_modules` is pnpm-managed: install with `pnpm add`, never `npm install` (there is no `package-lock.json`; `package.json` pins pnpm in `packageManager`). `npm run <script>` still works. pnpm refuses to run anything unless `allowBuilds` in `pnpm-workspace.yaml` holds real `true`/`false` values.

No test runner is configured yet. The pure rules are covered by `node`-run check scripts (Node 23+ strips the TS types): `src/lib/listing.check.mjs` (listing filters/sorts, every `stockState` branch), `cart-rules`, `order-rules`, `admin-rules` and `auth-validation` `.check.mjs` beside their modules, and `src/app/admin/admin-guard.check.mjs` (every admin page/action/data function checks the role). Run them all with `for f in $(find src -name "*.check.mjs"); do node $f; done`.

## Architecture

Next.js 16 App Router + React 19, Tailwind v4 (PostCSS plugin only — no `tailwind.config`; theme lives in `src/app/globals.css`), TypeScript strict, `@/*` → `src/*`.

**Data layer.** `src/db/index.ts` creates a single `db` over Neon's HTTP driver (`drizzle-orm/neon-http`) and throws at import time if `DATABASE_URL` is missing. That driver is stateless HTTP — no interactive transactions, so batch via `db.batch()` rather than `db.transaction()`. `DATABASE_URL` must be the **pooled** Neon string. `npm run build` needs it too: `generateStaticParams` reads product slugs from the database.

**Neon.** One environment by choice: the repo is linked (`.neon`, gitignored) to project `flat-frost-80736700`, branch **`production`**, and development, migrations and seeding all run against it. Get the URL with `neon connection-string production --pooled`. Link with `--no-env-pull`, because the default env pull writes into `.env`. `db:seed` **wipes and rewrites the live catalogue**: once real products exist, stop using it (or seed a throwaway branch instead).

**Schema.** `src/db/schema.ts` is the single schema file and the source of truth for `drizzle.config.ts`, the `db` client, and the Better Auth adapter. It holds the four Better Auth tables (`user`, `session`, `account`, `verification`, migration `0001`) plus the catalogue (`categories`, `products`, `product_images`); every further application table belongs in the same file. Renaming or dropping the Better Auth columns breaks auth. The auth block is CLI output kept verbatim. To change it (e.g. after adding a Better Auth plugin), run `npx auth@<better-auth version> generate --config src/lib/auth.ts --output <scratch file>` and paste the result in. The old `@better-auth/cli` package stopped at 1.4. Never point `--output` at `schema.ts`: it overwrites the catalogue. Conventions: camelCase TS keys mapped to snake_case columns via `casing: "snake_case"`, which must be set in **both** `drizzle.config.ts` and the `drizzle()` call, or migrations and queries disagree on column names; `uuid` primary keys with `defaultRandom()` on application tables, with `slug` as the unique public identifier every route and React key uses; declare each foreign key's `relations()` alongside the table.

**Catalogue.** Schema decisions the storefront depends on:

- **Money is integer cents** (`priceCents`, `compareAtCents`). Only `mapProduct()` in `src/lib/products.ts` divides by 100; components receive dollars and never see the column.
- **Stock is a quantity plus a flag** (`stockQuantity`, `madeToOrder`), never a stored state. The four states the UI speaks in are derived by `stockState()` in `src/lib/stock.ts`, which also owns `stockCopy` and `stockTone`; every surface (cards, product page, listing sort, admin stock filter) goes through it. Made-to-order with pieces on hand is `in_stock`, never "Only N left", because the bag allows 10 of it. `tsconfig.json` sets `allowImportingTsExtensions` so pure modules can value-import each other as `./x.ts` and still run in the `*.check.mjs` scripts under Node. `stockDetail` is editorial free text beside them. Stock is per product: with no variants, the size picker is a display-only list by category and sizes are not stocked.
- **Homepage order comes from `products.createdAt` descending**, not from a featured or "new" flag — the grid takes the newest 8 (a "rail" of the next 5 is not built yet). "New" (badge and `/new-arrivals`) is derived as the newest `NEW_COUNT` (12) by a subquery, never stored.
- **Categories carry the homepage "Collections" strip**: the ones with an `imageUrl` are what it renders, and piece counts are counted from `products`, never stored.
- **`product_images.alt` belongs to the row, not the asset** — the same URL is reused across products with different copy. `position` 0 is the packshot.
- Pages never touch `db` directly: they call the query functions in `src/lib/products.ts`, which return the mapped `Product` type. `src/lib/sample-data.ts` is static chrome (hero, atelier, services, nav, footer) plus `categoryDetails`/`detailsFor()`, the per-category size lists and care copy that the product page, the bag's size validation and checkout rely on; it holds no products. Listing filters/sorts are pure functions in `src/lib/listing.ts`, run in memory over one view's products. That is a deliberate ceiling: move them into the SQL `where` once a single view holds a few hundred products.
- **Categories are product types** (ready-to-wear, bags, shoes, accessories, jewellery). Department (`women`/`men`/`unisex`) is an enum column, and `isGift` a flag. Listing routes: `/collections/[slug]` (by category), `/women` and `/men` (department, both include unisex), `/gifts`, `/new-arrivals`; all share `src/components/product-listing.tsx`.- Drizzle relational queries: write the `with` block inline at each call site. Hoisting it into a shared `as const` config breaks result-shape inference. Relational queries alias the outer table, so raw subqueries inside `extras`/`orderBy` need their own alias (`from products p2`). The `extras` callback receives columns, not the table, so type its parameter as `{ col: AnyColumn }`.

**Migrations.** Versioned SQL committed under `drizzle/`, generated with `db:generate` and applied with `db:migrate`; `db:push` stays a dev-only escape hatch. Read the emitted SQL before applying it. `scripts/seed.ts` (run via `db:seed`, under `tsx` with `import "dotenv/config"`) is idempotent — it clears `product_images` → `products` → `categories` in that order, and backdates `createdAt` from a hardcoded base date so ordering is reproducible across runs.

**Auth.** `src/lib/auth.ts` is the server instance: Drizzle adapter, email/password with `requireEmailVerification` (no session until the link is clicked; duplicate sign-ups get the same generic reply as new ones). Sign-in, sign-up and sign-out run from client components through `src/lib/auth-client.ts` and the `/api/auth/[...all]` routes, **not** Server Actions calling `auth.api.*`: Better Auth's rate limiting only runs in its HTTP router, so server-side calls would bypass it. A `hooks.before` on `/sign-up/email` deletes an unverified account whose link has expired, so a stranger's sign-up can't reserve an address for good. Verification mail goes through `src/lib/email.ts` (Resend over `fetch`); email is "off" (`emailIsOff()`) when `RESEND_API_KEY`/`EMAIL_FROM` are missing **and** the app is in development or has `EMAIL_LINKS_ON_PAGE=true` (the internal test site). Then every email is only printed to the server log, the verification link is **shown on the sign-up page** (and in the unverified sign-in notice) via `getDevVerificationLink` in `src/lib/dev-email-actions.ts` (a public action that signs the link on demand for any unverified account, so anyone can verify any unverified address), and the success and order pages stop promising receipts or shipping emails. In production without that switch a missing key throws. Never set it for a real launch.

**Sessions and roles.** Server code reads the session only through `src/lib/session.ts`: `getSession()` (React `cache`, no cookie cache, so sign-out and role changes apply on the next request), `requireUser(next)` and `requireAdmin()` for pages, `assertAdmin()` for admin Server Actions and data functions (they are public endpoints, so they throw rather than redirect). Call these in every protected page and action, never only in a layout: layouts don't re-render on client navigation. There is no `proxy.ts`. Customers get a 404 from admin pages, so the routes aren't advertised. `user.role` (`customer` | `admin`) is a Better Auth `additionalField` with `input: false`; only `npm run auth:set-role -- <email> <role>` (the way to create the first admin) and the `/admin` page can change it, and an admin can't change their own role. A role change deletes that user's sessions in the same `db.batch`; `auth:set-role` refuses to promote an unverified email. Better Auth rate limiting is stored in Postgres (`rate_limit`, migration `0005`) and runs in production only (dev traffic has no client IP, so it would share one bucket); `customRules` keys omit the `/api/auth` base. Redirect targets from `?next=` go through `safeNext()` (same-site paths only).

**Admin.** `/admin/*` shares `src/app/admin/layout.tsx` (header plus `AdminNav`: Products, Stock, Categories, Orders, Accounts). The layout is **not** the access check: it renders its chrome only for admins, so a customer's 404 shows no admin navigation, and every page still starts with `await requireAdmin("/admin/…")`. Every admin Server Action (`src/app/admin/**/actions.ts`) and admin data function (`src/lib/users.ts`, `src/lib/admin-*.ts`) starts with `await assertAdmin()`. `node src/app/admin/admin-guard.check.mjs` enforces all three statically (including `export const` async actions and any `"use server"` file under `src/app/admin`), so a new route or action without the check fails. `/admin` checks the role, then redirects to `/admin/products`. Role management lives at `/admin/accounts`. `SectionNav` (`src/components/section-nav.tsx`) is the shared tabs/sidebar that both `AccountNav` and `AdminNav` render through.

**Admin products.** `/admin/products` (list, `?q=` name and `?category=` filters), `/admin/products/new` and `/admin/products/[id]` share `src/components/admin/product-form.tsx`. Validation is `parseProductForm` in `src/lib/admin-rules.ts` (pure; `node src/lib/admin-rules.check.mjs`). Prices are typed in dollars and parsed as **text** by `toCents` (no floats); the slug is derived from the name and can't be changed after create; image URLs must be `https://images.unsplash.com` (the only host `next.config.ts` allows). Writes go through `src/lib/admin-catalogue.ts`. An edit is ONE SQL statement (product plus its position-0 packshot upsert; other gallery images are untouched), and **stock is guarded**: the form posts the quantity it loaded (`expectedStock`). An untouched stock field isn't written, and a changed one only applies while stock still equals that number, so a sale decremented by the webhook while the form was open is never overwritten (the admin gets the new number and saves again). Every admin catalogue write calls `revalidatePath("/", "layout")`, because the storefront is ISR and must show edits at once. Duplicate slugs map from Postgres `23505` to a field error. Admin forms share `Section`, `Field`, `Check` and `Spinner` from `src/components/admin/form-parts.tsx`. `/admin/stock` saves through `updateStock` (one UPDATE, same `expectedStock` guard) and filters by `?q=` and `?state=` (`low_stock`/`sold_out`/`made_to_order`, derived in memory with the storefront's `stockState()`). `/admin/categories`: slug is `slugify(name)`, fixed at create; image URL and alt go together; delete only succeeds on an empty category (`restrict` FK, `23503` mapped to a message). Sizes still come from `categoryDetails` in `src/lib/sample-data.ts`, so an admin-created category is one-size until that file lists it.

**Bag.** The bag is DB-backed and signed-in only: one `cart_items` table keyed by `(user_id, product_id, size)`, no parent `carts` table, so there is no guest bag and nothing to merge on sign-in. `size` is the display-only size from `detailsFor()` (`""` for one-size categories); stock is per product, so a product's sizes share one allowance. `src/lib/cart.ts` is the only module that touches `db` for carts, the way `src/lib/products.ts` owns the catalogue; rules and shapes (`maxAllowed`, `lineMax`, `subtotalCents`, `BagLine`) live in `src/lib/cart-rules.ts` so client components can import them without pulling in `db` (`node src/lib/cart-rules.check.mjs` covers them). **`cart_items` stores no price**: amounts are read live from `products.priceCents` on every render, and forms send only a slug, a size and a quantity. The Server Actions in `src/lib/cart-actions.ts` are public endpoints: each reads the session, validates every field and re-checks live stock (`maxAllowed`: stock capped at 10, made-to-order always 10, sold out 0; the DB also checks `quantity between 1 and 10`). The bag holds no reservation: stock that drops after adding shows as a notice on `/bag` (`lineIssue`), the bag is never changed on read, and checkout must re-check. Products cascade to `cart_items`, so `db:seed` empties every bag.

**Checkout.** Stripe-hosted Checkout Sessions (test mode: "Maison sandbox"). `startCheckoutAction` in `src/lib/checkout-actions.ts` posts an **empty form**: it re-reads the bag with `getBag()` (the authoritative stock check; any `hasIssues` blocks checkout), snapshots it into a **pending order** (`createPendingOrder` in `src/lib/orders.ts`, our prices), and creates the session from that snapshot with `price_data`. There are no Stripe Products or Prices and no sync job; Stripe never receives an amount the browser supplied. Before creating a session it closes the user's older open sessions (an already-paid one is applied instead, so no payment is lost). Sessions expire after 30 minutes, which is also the accepted oversell window (no stock reservation). Never pass `payment_method_types` (dynamic payment methods), keep `integration_identifier`, and use a restricted `rk_` key with *Checkout Sessions: write*. `src/lib/stripe.ts` validates keys on first use, so the storefront builds and runs without them. Tax is off (Stripe Tax needs a registration) and shipping addresses are collected for the US only (`SHIP_TO`).

**Orders move forward only on Stripe-verified facts.** `applyCheckoutSession` in `src/lib/orders.ts` is the single fulfilment function. Its input is always a Checkout Session that came from Stripe itself, never from the browser: the webhook (`src/app/api/stripe/webhook/route.ts`, signature-verified over the raw body, handling `checkout.session.completed`, `async_payment_succeeded`, `async_payment_failed`, `expired` and `charge.refunded`; 500 when `STRIPE_WEBHOOK_SECRET` is unset, so Stripe retries) is the primary path. `/checkout/success` and the checkout action's older-session sweep are the **fallback** for a webhook that is late or never arrives (e.g. `stripe listen` not running): both `sessions.retrieve()` on the server with our key and apply it through `sessionEvent()`, which maps a fetched session onto the equivalent event (every fallback fetches the session with `expand: ["payment_intent"]`: a complete, unpaid session whose PaymentIntent is back at `requires_payment_method` or `canceled` maps to `async_payment_failed`, so a missed failure webhook can't leave an order `processing` and block checkout; the restricted key can read that expanded PaymentIntent). The `session_id` in the success URL is only a lookup key; the page 404s unless `client_reference_id` is the signed-in user, and still shows "confirming" (polling with `AutoRefresh`) if the order is pending while Stripe says complete. If the sweep (`unsettledOrdersFor`: pending and processing) finds an older order paid, checkout stops and asks the customer to review the bag; if one is still `processing`, checkout stops until it settles, so the same pieces are never charged twice. The sweep **fails closed**: any Stripe error while checking or expiring an older session stops checkout ("try again in a moment"), because that session may still be payable; only `resource_missing` (the session doesn't exist for this key, so it can't be paid) expires the order and lets checkout continue. Status transitions come from `nextStatus()` in `src/lib/order-rules.ts` (`pending → processing/paid/payment_failed/expired`, forward only, with an unknown `payment_status` never counting as paid; `node src/lib/order-rules.check.mjs`). Each transition is **one SQL statement** (CTEs; neon-http has no transactions) guarded by `status = <current>`. Only the call that actually moves an order to `paid` decrements stock (made-to-order included, floored at 0) and deletes the paid lines from the bag. `stock_shortfall` is read from the decrement itself (the `dec`/`short` CTEs see the locked row, not the snapshot, so a concurrent last-unit race is caught; made-to-order is never short) and written by `t` in the **same** statement: `g` locks the order row (`for update`, re-checked against the committed status) before the decrement, and `t` reads `short`, so nothing that can fail runs after the order is paid and a Stripe retry stays safe. Any call that finds an order `paid` runs `revalidatePath("/", "layout")` so ISR stock is fresh; Next throws on that during a page render, so it is swallowed there and the webhook covers it. That guard is what makes duplicate or concurrent deliveries harmless; there is no event table. A call that loses the race re-reads the status and, if the winner moved the order somewhere this event can still advance (pending → processing while a payment-succeeded event read pending), applies it once more, because a webhook answered 200 is never redelivered. The webhook resolves both `STRIPE_WEBHOOK_SECRET` and `STRIPE_SECRET_KEY` before verifying, so a missing key is a 500 ("not configured"), not a 400 bad signature. The webhook returns 500 on a database error so Stripe retries. `order_items` snapshot name, slug, size and unit price (`product_id` is `set null`), and `orders.user_id` is `restrict`, so re-seeding or catalogue edits never break order history. Keep `/api/**` out of any future `src/proxy.ts` matcher: Stripe sends no cookie. **Order history** is `/account/orders` (`listOrdersForUser`, expired checkouts hidden) and `/account/orders/[id]`; both scope by the session's user id, so another customer's order id is a plain 404. The detail page, like `/checkout/success`, re-checks a pending or processing order against Stripe (`sessions.retrieve` + `sessionEvent`) so a missed webhook never leaves it stale; a Stripe error just shows the stored state. Items, totals and delivery render through `OrderDetails` (`src/components/order-details.tsx`), shared with `/checkout/success`.

**Fulfilment is separate from payment.** `orders.status` stays Stripe-only; `orders.fulfilment_status` (`unfulfilled → shipped → delivered`, or `unfulfilled → cancelled`; migration `0006`) is admin-only, for paid orders, via `nextFulfilment()` in `order-rules.ts`. Each change in `src/lib/admin-orders.ts` is one UPDATE guarded on `status = 'paid'` and the expected from-state; a refused one returns the current state. Cancel records state only: the refund is issued in the Stripe Dashboard. Order emails (confirmation, shipped, cancelled) are written in `src/lib/order-emails.ts` and sent through `notifyCustomer` in `orders.ts`, which never throws; the confirmation goes from `applyCheckoutSession` only when that call moved the order to paid, the others only after the guarded UPDATE returned a row, so none can double-send. `getOrder(id)` has no ownership check (admin and email only); customer pages use `getOrderForUser`.

**Refunds are issued in the Stripe Dashboard, never in-app** (the restricted key stays Checkout-only). `orders.refunded_cents` (migration `0007`) mirrors the cumulative `charge.amount_refunded` from the `charge.refunded` webhook via `applyChargeRefund`: one statement, paid orders found by PaymentIntent, guarded by `refunded_cents < $amount`, so it only rises and duplicates or out-of-order deliveries are no-ops (a refund email goes on each rise). `status` stays `paid`; wording comes from `refundLabel()` in `order-rules.ts`. Known gaps: a refund that later fails still counts, and nothing restocks automatically (use `/admin/stock`).

**Only `/` and `/products/[slug]` are static (ISR, `revalidate = 300`; product pages also `generateStaticParams`).** Every listing (`/collections/[slug]`, `/new-arrivals`, `/women`, `/men`, `/gifts`, `/search`) reads `searchParams` for its filters, so it renders per request. The header (the inline `Header()` in `src/app/layout.tsx`) shows no bag count anywhere, on purpose: a server read of `headers()` in the root layout would make the two static routes dynamic. If a count is ever wanted, fetch it from a client component after hydration.

**Money formatting.** `currency` in `src/lib/format.ts` rounds to whole dollars and is **catalogue-only**. Anything derived from cents — bag, checkout, receipts — uses `formatCents`, or `$99.99` renders as `$100` next to a Stripe page that says otherwise.

Env: copy `.env.example` → `.env`. Claude cannot read or write `.env` (denied by permissions), so the user pastes secrets such as `DATABASE_URL` themselves. Auth needs `BETTER_AUTH_SECRET` (`openssl rand -base64 32`) and `BETTER_AUTH_URL` (the app's origin, or verification links break); sending real email needs `RESEND_API_KEY` and `EMAIL_FROM`. Checkout additionally needs `STRIPE_SECRET_KEY` (a restricted `rk_` key with Checkout Sessions: write) and `STRIPE_WEBHOOK_SECRET` (from `stripe listen --events checkout.session.completed,checkout.session.async_payment_succeeded,checkout.session.async_payment_failed,checkout.session.expired,charge.refunded --forward-to localhost:3000/api/stripe/webhook` locally; current CLIs refuse to start without `--events`. The secret is stable per machine, see `stripe listen --print-secret`; or the endpoint's own signing secret when deployed). `src/lib/stripe.ts` validates these on first use rather than at import, so the storefront still builds and runs without them — only checkout and the webhook fail.

## Next.js 16 notes

Route params and `searchParams` are Promises and must be awaited. Layouts/pages use the globally generated `LayoutProps<"/route">` / `PageProps<"/route">` types (see `src/app/layout.tsx`) — these are emitted into `.next/types`, so a route's types only exist after a dev server or build has run. Read `node_modules/next/dist/docs/` before relying on remembered APIs. After renaming a dynamic segment (e.g. `[id]` → `[slug]`), restart the dev server: it keeps the old route cached and throws "different slug names for the same dynamic path". Stale `.next/types` from an old `next build` break `tsc` the same way. Only one `next dev` may run per `distDir`, and Tailwind scans every folder that isn't gitignored: a second build output under another name (e.g. for a test server) gets its binaries scanned into garbage classes that break `globals.css`, and the broken CSS survives in `.next/dev` until that folder is deleted.
